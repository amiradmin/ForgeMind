# Maintenance Domain Models

## 1. Overview

The Maintenance Domain is responsible for managing maintenance activities associated with industrial assets within ForgeMind.

The domain follows the ForgeMind architectural principles:

* Modular Monolith
* Domain-Driven Design
* Clean Architecture
* Testability
* Documentation First

The Maintenance Domain is implemented as an independent Django application under:

```text
backend/apps/maintenance/
```

The domain owns maintenance-related business concepts and does not own the Asset entity itself.

The Asset entity remains owned by the Asset Domain.

---

## 2. Domain Boundaries

The relationship between the Asset and Maintenance domains is:

```text
                    Asset Domain
                         │
                         │ owns
                         ▼
                       Asset
                         │
                         │ referenced by
                         ▼
                Maintenance Domain
                         │
          ┌──────────────┼──────────────┐
          │              │              │
          ▼              ▼              ▼
  MaintenancePlan  MaintenanceRequest  WorkOrder
```

The Asset Domain is responsible for:

* Organization
* Plant
* Area
* Asset
* AssetType
* Asset Metadata
* Asset Lifecycle
* Asset Documents

The Maintenance Domain is responsible for:

* Maintenance Plans
* Maintenance Requests
* Work Orders
* Maintenance-specific business rules
* Maintenance lifecycle management

The Maintenance Domain must not own or duplicate the core Asset entity.

---

## 3. Core Domain Entities

The initial Maintenance Domain consists of three primary entities:

1. `MaintenancePlan`
2. `MaintenanceRequest`
3. `WorkOrder`

A separate `MaintenanceHistory` model will not be introduced in the initial implementation.

Maintenance history will be derived from completed `WorkOrder` records.

---

## 4. MaintenancePlan

### Purpose

`MaintenancePlan` defines planned and recurring maintenance activities for an Asset.

A maintenance plan represents a schedule or policy that determines when maintenance should be performed.

Examples include:

* Inspect a pump every 30 days
* Service a compressor every 3 months
* Replace a filter every 6 months
* Perform annual equipment inspection

### Relationships

```text
Asset
  │
  └── 1 ───────── N ── MaintenancePlan
```

An Asset may have multiple maintenance plans.

### Fields

```text
MaintenancePlan
├── id
├── is_active
├── created_at
├── updated_at
├── asset
├── name
├── description
├── maintenance_type
├── frequency
├── frequency_unit
├── start_date
└── next_due_date
```

### Field Definitions

| Field              | Type       | Description                                              |
| ------------------ | ---------- | -------------------------------------------------------- |
| `id`               | UUID       | Primary key inherited from `BaseModel`                   |
| `is_active`        | Boolean    | Indicates whether the plan is active                     |
| `created_at`       | DateTime   | Creation timestamp                                       |
| `updated_at`       | DateTime   | Last update timestamp                                    |
| `asset`            | ForeignKey | Asset associated with the plan                           |
| `name`             | String     | Human-readable plan name                                 |
| `description`      | Text       | Optional description                                     |
| `maintenance_type` | Enum       | Type of maintenance                                      |
| `frequency`        | Integer    | Number of frequency units between maintenance activities |
| `frequency_unit`   | Enum       | Days, weeks, months, or years                            |
| `start_date`       | Date       | Date from which the plan becomes effective               |
| `next_due_date`    | Date       | Next scheduled maintenance date                          |

### Asset Relationship

The relationship to Asset uses `PROTECT`:

```python
asset = models.ForeignKey(
    "assets.Asset",
    on_delete=models.PROTECT,
    related_name="maintenance_plans",
)
```

An Asset must not be deleted while maintenance plans reference it.

## 5. MaintenanceRequest

### Purpose

`MaintenanceRequest` represents a maintenance need or request associated with an Asset.

A request can be:

* Manually created by a user
* Generated from a Maintenance Plan
* Generated by an automated system
* Generated by AI or predictive maintenance systems
* Generated by future IoT or Computer Vision integrations

### Relationships

```text
Asset
  │
  └── 1 ───────── N ── MaintenanceRequest
                              │
                              │ optional
                              ▼
                     MaintenancePlan
```

A Maintenance Request may originate from a Maintenance Plan, but it does not have to.

### Fields

```text
MaintenanceRequest
├── id
├── is_active
├── created_at
├── updated_at
├── asset
├── maintenance_plan
├── title
├── description
├── maintenance_type
├── priority
├── status
├── requested_by
├── requested_at
└── resolved_at
```

### Field Definitions

| Field              | Type                 | Description                            |
| ------------------ | -------------------- | -------------------------------------- |
| `id`               | UUID                 | Primary key inherited from `BaseModel` |
| `is_active`        | Boolean              | Indicates whether the record is active |
| `created_at`       | DateTime             | Creation timestamp                     |
| `updated_at`       | DateTime             | Last update timestamp                  |
| `asset`            | ForeignKey           | Asset requiring maintenance            |
| `maintenance_plan` | ForeignKey, nullable | Optional source maintenance plan       |
| `title`            | String               | Short description of the request       |
| `description`      | Text                 | Detailed description                   |
| `maintenance_type` | Enum                 | Type of maintenance                    |
| `priority`         | Enum                 | Maintenance priority                   |
| `status`           | Enum                 | Current request status                 |
| `requested_by`     | ForeignKey, nullable | User who created the request           |
| `requested_at`     | DateTime             | Time the request was submitted         |
| `resolved_at`      | DateTime, nullable   | Time the request was resolved          |

### Maintenance Plan Relationship

The relationship to `MaintenancePlan` is optional.

```python
maintenance_plan = models.ForeignKey(
    "maintenance.MaintenancePlan",
    null=True,
    blank=True,
    on_delete=models.SET_NULL,
    related_name="requests",
)
```

This supports both:

```text
MaintenancePlan
      │
      ▼
MaintenanceRequest
```

and:

```text
User / System / AI
      │
      ▼
MaintenanceRequest
```

### Requested By

The `requested_by` relationship references the project's custom User model through `AUTH_USER_MODEL`.

```python
requested_by = models.ForeignKey(
    settings.AUTH_USER_MODEL,
    null=True,
    blank=True,
    on_delete=models.SET_NULL,
    related_name="maintenance_requests",
)
```

The relationship is nullable to support automated maintenance requests created by future AI, IoT, Computer Vision, or predictive maintenance systems.

## 6. WorkOrder

### Purpose

`WorkOrder` represents the actual maintenance work that must be performed or has been performed on an Asset.

A Work Order may originate from a Maintenance Request or may be created directly.

### Relationships

```text
Asset
  │
  └── 1 ───────── N ── WorkOrder
                           ▲
                           │ optional
                           │
                 MaintenanceRequest
```

### Fields

```text
WorkOrder
├── id
├── is_active
├── created_at
├── updated_at
├── asset
├── maintenance_request
├── title
├── description
├── maintenance_type
├── priority
├── status
├── assigned_to
├── scheduled_start
├── scheduled_end
├── started_at
├── completed_at
└── completion_notes
```

### Field Definitions

| Field                 | Type                 | Description                            |
| --------------------- | -------------------- | -------------------------------------- |
| `id`                  | UUID                 | Primary key inherited from `BaseModel` |
| `is_active`           | Boolean              | Indicates whether the record is active |
| `created_at`          | DateTime             | Creation timestamp                     |
| `updated_at`          | DateTime             | Last update timestamp                  |
| `asset`               | ForeignKey           | Asset being maintained                 |
| `maintenance_request` | ForeignKey, nullable | Optional originating request           |
| `title`               | String               | Short description of the work          |
| `description`         | Text                 | Detailed work description              |
| `maintenance_type`    | Enum                 | Type of maintenance                    |
| `priority`            | Enum                 | Work priority                          |
| `status`              | Enum                 | Current Work Order status              |
| `assigned_to`         | ForeignKey, nullable | User responsible for the work          |
| `scheduled_start`     | DateTime, nullable   | Planned start time                     |
| `scheduled_end`       | DateTime, nullable   | Planned end time                       |
| `started_at`          | DateTime, nullable   | Actual start time                      |
| `completed_at`        | DateTime, nullable   | Actual completion time                 |
| `completion_notes`    | Text                 | Notes recorded after completion        |

### Maintenance Request Relationship

The relationship is optional:

```python
maintenance_request = models.ForeignKey(
    "maintenance.MaintenanceRequest",
    null=True,
    blank=True,
    on_delete=models.SET_NULL,
    related_name="work_orders",
)
```

This supports:

```text
MaintenanceRequest
      │
      ▼
WorkOrder
```

as well as:

```text
Direct Work Order
      │
      ▼
WorkOrder
```

### Assigned User

The `assigned_to` relationship references the project's custom User model.

```python
assigned_to = models.ForeignKey(
    settings.AUTH_USER_MODEL,
    null=True,
    blank=True,
    on_delete=models.SET_NULL,
    related_name="assigned_work_orders",
)
```

A Work Order must remain available even if the assigned user is later removed or deactivated.

## 7. Maintenance Types

Maintenance types are represented using a Django `TextChoices` enumeration.

Initial values:

```text
PREVENTIVE
CORRECTIVE
```

### Preventive Maintenance

Maintenance performed according to a predefined schedule or plan to reduce the probability of equipment failure.

Examples:

* Scheduled inspection
* Lubrication
* Filter replacement
* Periodic servicing

### Corrective Maintenance

Maintenance performed in response to an identified problem or failure.

Examples:

* Equipment breakdown
* Component failure
* Unexpected malfunction

The initial implementation will not create separate models for preventive and corrective maintenance.

Both are represented by the `maintenance_type` field.

Future types may include:

```text
PREDICTIVE
CONDITION_BASED
EMERGENCY
```

These should only be added when actual product requirements require them.

## 8. Maintenance Priority

Maintenance priority is represented using a shared enumeration.

Initial values:

```text
LOW
MEDIUM
HIGH
CRITICAL
```

### Priority Definitions

| Priority   | Description                                                                              |
| ---------- | ---------------------------------------------------------------------------------------- |
| `LOW`      | Maintenance can be scheduled without significant operational impact                      |
| `MEDIUM`   | Maintenance should be addressed within a reasonable timeframe                            |
| `HIGH`     | Maintenance requires prompt attention                                                    |
| `CRITICAL` | Maintenance requires immediate attention due to significant operational or safety impact |

## 9. Maintenance Frequency

Maintenance plans use two fields to define recurrence:

```text
frequency
frequency_unit
```

Example:

```text
frequency = 3
frequency_unit = MONTHS
```

This represents:

```text
Every 3 months
```

Initial frequency units:

```text
DAYS
WEEKS
MONTHS
YEARS
```

A complex scheduling engine is intentionally excluded from the initial domain model.

Scheduling logic can be introduced later as a dedicated service or scheduling subsystem.

## 10. Maintenance Request Lifecycle

Initial request statuses:

```text
OPEN
  │
  ▼
IN_REVIEW
  │
  ├──────────────► REJECTED
  │
  ▼
APPROVED
  │
  ▼
CONVERTED
  │
  ▼
CLOSED
```

### Status Definitions

| Status      | Description                                     |
| ----------- | ----------------------------------------------- |
| `OPEN`      | Request has been created and awaits review      |
| `IN_REVIEW` | Request is currently being evaluated            |
| `APPROVED`  | Request has been approved for maintenance       |
| `REJECTED`  | Request has been rejected                       |
| `CONVERTED` | Request has resulted in one or more Work Orders |
| `CLOSED`    | Request lifecycle is complete                   |

The exact transition rules will be implemented in the Maintenance service layer rather than directly inside Django views.

---

## 11. Work Order Lifecycle

Initial Work Order statuses:

```text
OPEN
  │
  ▼
ASSIGNED
  │
  ▼
IN_PROGRESS
  │
  ▼
COMPLETED
```

An open or assigned Work Order may also be cancelled:

```text
OPEN ─────────► CANCELLED

ASSIGNED ─────► CANCELLED
```

### Status Definitions

| Status        | Description                                         |
| ------------- | --------------------------------------------------- |
| `OPEN`        | Work Order has been created but is not yet assigned |
| `ASSIGNED`    | Work Order has been assigned to a user              |
| `IN_PROGRESS` | Maintenance work is currently being performed       |
| `COMPLETED`   | Maintenance work has been completed                 |
| `CANCELLED`   | Work Order will not be completed                    |

Status transition rules will be enforced by the Maintenance service layer.

## 12. Maintenance History

A separate `MaintenanceHistory` model will not be implemented in the initial version.

Instead, maintenance history is derived from completed Work Orders.

```text
Asset
  │
  ▼
WorkOrders
  │
  ├── OPEN
  ├── ASSIGNED
  ├── IN_PROGRESS
  ├── COMPLETED  ◄── Maintenance History
  └── CANCELLED
```

This approach provides a single source of truth.

A completed Work Order contains:

* Asset
* Maintenance Type
* Priority
* Work description
* Assigned User
* Start time
* Completion time
* Completion notes

Therefore, completed Work Orders can be queried as the maintenance history for an Asset.

A dedicated historical event model may be introduced in the future if ForgeMind requires:

* Immutable maintenance events
* Detailed maintenance activity logs
* Event sourcing
* Integration with the Audit Domain
* Regulatory traceability

Such a model is intentionally outside the scope of the initial Maintenance Domain implementation.

## 13. Asset Deletion Policy

Maintenance records reference Assets using `PROTECT`.

The following relationships use:

```python
on_delete=models.PROTECT
```

```text
Asset
  │
  ├── MaintenancePlan
  ├── MaintenanceRequest
  └── WorkOrder
```

An Asset cannot be deleted while maintenance records reference it.

This prevents accidental deletion of historical maintenance information.

Asset lifecycle management should be handled through the Asset Domain.

For example, an Asset can be marked as:

```text
OUT_OF_SERVICE
```

or:

```text
RETIRED
```

instead of being physically deleted from the database.

---

## 14. User Deletion Policy

User references such as:

* `requested_by`
* `assigned_to`

use:

```python
on_delete=models.SET_NULL
```

This ensures that deleting or deactivating a User does not delete Maintenance records.

Maintenance history must remain intact even when the original User is no longer available.

## 15. BaseModel Integration

All Maintenance Domain entities inherit from the shared ForgeMind `BaseModel`.

```python
class BaseModel(models.Model):
    id = models.UUIDField(
        primary_key=True,
        default=uuid.uuid4,
        editable=False,
    )

    is_active = models.BooleanField(default=True)

    created_at = models.DateTimeField(auto_now_add=True)

    updated_at = models.DateTimeField(auto_now=True)

    class Meta:
        abstract = True
```

Therefore:

```text
MaintenancePlan
MaintenanceRequest
WorkOrder
```

automatically inherit:

* UUID primary key
* Active state
* Creation timestamp
* Update timestamp

No duplicate definitions of these fields should be added to the Maintenance models.

## 17. Domain Ownership

The following ownership boundaries are mandatory:

```text
Asset Domain
├── Organization
├── Plant
├── Area
├── Asset
├── AssetType
├── Asset Metadata
├── Asset Lifecycle
└── Asset Documents


Maintenance Domain
├── MaintenancePlan
├── MaintenanceRequest
├── WorkOrder
├── Maintenance Types
├── Maintenance Priorities
├── Maintenance Statuses
└── Maintenance Business Rules
```

The Maintenance Domain may reference an Asset but must not duplicate or take ownership of the Asset model.

## 19. Implementation Scope

The implementation following this design should create:

```text
backend/apps/maintenance/
│
├── __init__.py
├── admin.py
├── apps.py
│
├── models/
│   ├── __init__.py
│   ├── enums.py
│   ├── maintenance_plan.py
│   ├── maintenance_request.py
│   └── work_order.py
│
└── tests/
    ├── __init__.py
    ├── factories.py
    └── test_models.py
```

The following are explicitly outside the scope of this design issue:

* REST API
* Serializers
* ViewSets
* Permissions
* Business services
* Background tasks
* Automatic maintenance scheduling
* AI-generated maintenance requests
* Predictive maintenance
* Computer Vision integration

These capabilities will be implemented in subsequent issues.

## 20. Architectural Decision Summary

| Decision                  | Choice                             |
| ------------------------- | ---------------------------------- |
| Architecture              | Modular Monolith                   |
| Domain                    | Independent Maintenance Domain     |
| Primary entities          | Plan, Request, Work Order          |
| Asset ownership           | Asset Domain                       |
| Asset relationship        | ForeignKey with `PROTECT`          |
| User relationship         | `AUTH_USER_MODEL`                  |
| User deletion             | `SET_NULL`                         |
| Primary key               | UUID via `BaseModel`               |
| Soft-active state         | `is_active` via `BaseModel`        |
| Maintenance history       | Derived from completed Work Orders |
| Maintenance type          | Enum                               |
| Priority                  | Enum                               |
| Request status            | Enum                               |
| Work Order status         | Enum                               |
| Scheduling engine         | Deferred                           |
| Maintenance History model | Deferred                           |
| API                       | Deferred                           |
| Business logic            | Deferred to Service layer          |

---

## 21. Conclusion

The initial Maintenance Domain design provides a clear separation between Asset Management and Maintenance Management while keeping the architecture simple enough for the current Modular Monolith implementation.

The core model is:

```text
Asset
  │
  ├── MaintenancePlan
  │
  ├── MaintenanceRequest
  │
  └── WorkOrder
```

Maintenance history is represented by completed Work Orders rather than a duplicated history table.

This design provides a foundation for future capabilities such as:

* Preventive Maintenance
* Corrective Maintenance
* Predictive Maintenance
* AI-generated Maintenance Requests
* IoT-based maintenance detection
* Computer Vision-based failure detection
* Maintenance scheduling
* Maintenance analytics

The next implementation step is to create the Django Maintenance models, migrations, factories, and model tests based on this specification.
